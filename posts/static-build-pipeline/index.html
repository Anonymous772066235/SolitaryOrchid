一个够用的静态构建脚本

不装任何运行时，只用系统自带的脚本把 Markdown 变成整站 HTML：解析 front matter、转换正文、生成归档与订阅源。

这个站没有 Node、没有打包器，构建靠一个系统脚本完成。虽然简陋，但覆盖了写博客真正需要的部分。

输入与输出

输入是两类东西：

  • src/content/posts/*.md：每篇文章一个文件，开头是 front matter
  • src/layouts/*.html：模板，用 {{TITLE}}、{{BODY}} 这类占位符

输出是整站静态文件：首页、文章列表、每篇文章、sitemap.xml、feed.xml、404.html。

front matter 解析

只用最朴素的分隔符与键值对：

---
title: 文章标题
date: 2026-11-13
tags: 可视化, 前端
summary: 一句话摘要
---

解析时把第一对 --- 之间的内容按行切开，用 键: 值 建立字典，剩下的部分是正文。

Markdown 子集

完整实现 Markdown 规范没有必要。实际写作中，九成内容只用这些语法：二级三级标题、段落、无序列表、代码块、引用、分隔线，以及行内粗体、行内代码和链接。

转换的关键是顺序：

  1. 先把代码块抽出来做占位，避免里面的 # 和 * 被当成标题或强调
  2. 再逐行处理块级元素（标题、列表、引用、分隔线）
  3. 剩下的连续行合成段落
  4. 最后统一处理行内语法，并把代码块还原成

顺手在生成标题时收集编号，就能拼出文章目录。

相对路径的处理

站点既可能部署在域名根目录，也可能在 // 这样的子路径下。所以模板里所有链接都写成 {{ROOT}} 占位，构建时按输出深度替换：

  • 根目录的页面 → ./
  • posts// 下的文章 → ../../

这样同一套模板可以放到任意层级，不需要知道最终的域名。

什么不做

  • 不做增量构建：全量重建不到一秒，没必要
  • 不做模板继承：三个模板各写一份，比实现继承逻辑更省心
  • 不做插件系统：需要新能力时直接改脚本

顺着这个思路，评论可以用第三方脚本挂载，搜索可以用构建期生成的索引，都无需把整个站点改造成 SPA。
